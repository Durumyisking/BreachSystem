# 직접 구현 마일스톤: 네트워크 벽 파괴 플러그인

## 1. 완성할 결과

**GameFeature로 활성화되는 Unreal 벽 파괴 플러그인. 데디케이트 서버가 파괴를 판정하고, 여러 클라이언트와 중도 접속자가 같은 파괴 상태와 충돌을 공유한다.**

피스톨은 작은 원형 구멍, 해머는 큰 사각형 구멍을 만든다. 가까운 구멍은 합쳐지고, 지지와 끊긴 가운데 조각은 사라지며, 한 구역에 피격이 누적되면 큰 덩어리가 부서진다. 공개된 시즈 기술 자료를 참고한 자체 설계이며, 시즈 내부 구현의 완전한 재현이라고 주장하지 않는다.

이 문서는 사용자가 직접 구현하기 위한 과제와 검증 순서다. 정답 코드나 완성된 클래스 골격은 제공하지 않는다. 기존 C++·에셋·빌드 설정을 변경한 문서도 아니다.

### 최종 범위의 제안과 가정

- 평평한 직사각형 단일 벽 패널부터 완성한다. 임의의 곡면 StaticMesh를 자동 변환하는 기능은 포함하지 않는다.
- 원·사각형 단면, 고정된 벽 두께, 벽 법선 방향 관통을 지원한다. 사선 탄도의 앞뒤 구멍 이동까지 재현하는 것은 확장 과제다.
- 회전과 양수 비균일 Scale은 지원한다. 런타임 벽 이동·크기 변경, 음수 Scale은 첫 완성 범위에서 제외한다.
- 게임의 HP Damage와 벽의 누적 파괴량은 의미를 구분한다. 둘을 연결할지는 게임 정책에서 결정한다.
- 기본 파괴 계산은 BreachSystem 플러그인, 게임에 장착하는 기능은 별도 GameFeature에 둔다는 구성을 제안한다. GameFeature 이름은 구현 때 정한다.
- GameFeature는 매치 시작 전에 활성화하고, 라운드 종료·월드 정리 시 비활성화하는 정책으로 시작한다. 전투 도중 임의의 핫 언로드는 요구하지 않는다.
- 최종 실행 증거는 실제 Server 빌드 프로세스와 게임 클라이언트다. PIE 테스트만으로 완료하지 않는다.
- 최초 네트워크 버전은 서버가 확정한 2D 상태를 전달한다. 이벤트 재연·압축은 측정 후 선택한다.
- 핵심 완료에 온라인 매칭, 클라우드 배포, GAS, Linux 서버, 물리 파편 동기화, 치트 방지 제품, 사격 지연 보상까지 요구하지 않는다.

가정이 원하는 결과와 다르면 해당 단계 시작 전에 문서를 수정한다. 범위를 줄이는 대신 핵심 목표인 플러그인·GameFeature·데디케이트 서버·중도 접속은 끝까지 완성한다.

## 3. 직접 구현하며 배우는 방식

한 번에 아래 단계 전체를 코딩하지 않는다. 각 단계의 작은 작업 하나를 고르고 다음 순서를 반복한다.

1. 입력과 예상 출력을 종이에 그린다. 어떤 객체가 상태를 소유하는지 적는다.
2. 필요한 개념만 공부한다. 엔진 소스·공식 문서에서 사용할 함수의 계약을 읽는다.
3. 가장 작은 예제를 직접 구현한다. 한 구멍이 되기 전에 총기 시스템 전체를 연결하지 않는다.
4. 실패하기 쉬운 입력 하나를 추가한다. 결과를 그림·로그·테스트로 확인한다.
5. 왜 통과하는지 본인의 말로 설명하고 완료 조건에 증거를 남긴다.

AI가 필요할 때는 “정답 코드를 작성해 줘”보다 “이 입력에서 내 예상이 틀린 이유를 힌트로 알려 줘”, “이 함수의 소유권만 검토해 줘”, “빠진 경계 사례를 찾아 줘”처럼 범위를 좁힌다. 이 원칙은 학습 방식의 제안이며 필수 승인 절차는 아니다.

직접 구현한다는 이유로 모든 기반 알고리즘까지 새로 만들 필요는 없다. 폴리곤 클리핑·구멍 포함 삼각분할은 엔진 또는 검증된 라이브러리를 사용해도 된다. 선택 이유, 입력 조건, 실패 처리, 자신이 만든 연결·게임 규칙을 설명할 수 있어야 한다. 알고리즘 자체를 공부하려면 단순 다각형 Ear Clipping을 작은 연습으로 구현하고, 실사용 요구와 구분한다.

마일스톤마다 완료 상태는 `코드 작성 → 빌드 → 기능 검증 → 증거 저장`으로 따로 기록한다. 시간이 부족한 날은 작은 작업 중간에서 멈추되, 다음 단계로 완료 표시를 넘기지 않는다. 고정 주차보다 완료 조건을 기준으로 진행한다.

## M00. 책임과 검증 기준부터 정하기

**배울 것:** 상태의 주인, 원본 데이터와 파생 데이터, 입력·처리·출력 분리.

**직접 할 일**

- [v] 기존 `FireShot → Damage 전달 → ApplyBreachHit → 프록시 갱신`을 읽고 호출 순서를 한 장에 그린다.
- [v] 새 흐름의 소유자를 적는다: 게임은 무기 수치, Source는 단면, 벽은 남은 영역과 누적 손상, 서버는 판정, 클라이언트는 표현.
- [v] 벽 ID, 초기 패널 규격, 남은 영역, 상태 버전의 의미를 정의한다. 실제 클래스명은 아직 확정하지 않는다.
- [v] 기존 테스트 맵 또는 별도 작은 실험 맵에 벽 한 장만 준비한다. 첫 피격·반복·겹침·테두리·고리·전체 제거 위치를 고정한다.
- [v] 동일 입력을 다시 넣을 수 있는 피격 목록과 기록 양식을 만든다. 눈대중 마우스 클릭만으로 비교하지 않는다.
- [v] 사용할 단위, 관통 방향, 옆면 피격 정책을 적는다. 첫 버전은 앞뒤 면만 허용하고 옆면은 무시하는 정책을 제안한다.

**완료 조건:** 메시가 없어도 벽의 남은 영역을 설명할 수 있고, 누구의 데이터가 어느 순간 바뀌는지 그릴 수 있다.

**설명 질문:** “메시를 지웠다가 다시 만들어도 파괴 상태를 복원하려면 무엇이 남아 있어야 할까?”

**남길 자료:** 책임 그림, 지원 범위 한 페이지, 고정 피격 목록. 이후 성능 비교의 기준이다.

## M01. 서버 실행 가능성을 먼저 확인하기

**배울 것:** Game/Editor/Server Target, build·cook·package 차이, authority·possession·복제의 기본.

**직접 할 일**

- [v] 사용 엔진이 실제 Server Target 빌드를 지원하는지 확인한다. 폴더 이름이나 소스 헤더 존재만으로 소스 빌드라고 단정하지 않는다.
- [v] Server Target을 추가하고 프로젝트의 `BuildProject.bat`에 대상 선택을 넣는다. 현재 Editor 기본 경로는 유지한다.
- [ ] 프로젝트 빌드는 항상 루트 `BuildProject.bat`를 통한다. IDE Build나 엔진 Build.bat 직접 실행으로 우회하지 않는다. cook/package 절차도 선택한 방식과 인자를 기록한다.
- [ ] 최소 맵을 cook하고 Server 실행 파일을 구동한다. 서버 기본 맵과 클라이언트 연결 주소를 고정한다.
- [ ] 클라이언트 2개가 접속하고 서로 다른 Pawn을 소유하도록 만든다. 화면·로컬 PlayerController가 없는 서버에서 UI·카메라 경로가 실행되지 않게 점검한다.
- [ ] 현재 템플릿의 이동·스폰·무기 소유가 네트워크를 지원하는지 확인한다. 필요한 최소 스폰·소유·이동부터 구현한다.

**완료 조건:** 에디터의 서버 흉내가 아니라 실제 headless 서버에 클라이언트 2개가 접속하고, 서로의 이동을 확인한다. 아직 벽 파괴 복제는 필요 없다.

**설명 질문:** “서버에는 내 화면이 없는데, 어떤 데이터로 플레이어를 식별하고 판정할까?”

**남길 자료:** 엔진/프로젝트 버전, 빌드·실행 방법, 접속 로그, 서버+2클라이언트 영상. 공식 서버 가이드는 소스 빌드를 전제로 한다. [Epic 서버 설정 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/setting-up-dedicated-servers-in-unreal-engine)

## M02. 피격점을 벽의 2D 좌표로 옮기기

**배울 것:** 기준점과 기저 벡터, 내적, 월드↔패널↔컴포넌트 로컬 좌표.

**직접 할 일**

- [ ] 패널 원점·가로·세로·법선·두께를 정의한다. 양수 비균일 Scale을 적용한 실제 월드 크기를 구한다.
- [ ] 월드 피격점을 2D로 옮기고 다시 월드로 복원한다. 원래 점과 복원 점을 디버그 표시한다.
- [ ] 반지름으로 원형 다각형, 전체 가로·세로 크기로 사각형을 만든다. 동일 모양 정점은 바인딩 때 캐시한다.
- [ ] 단면의 회전 기준을 고정한다. 사각형 가로·세로가 앞뒤 피격에 따라 갑자기 바뀌지 않게 한다.
- [ ] 평면 단면 연산에서 기존 커터 Depth·월드 AABB 길이 계산이 왜 필요 없는지 설명한다.

**완료 조건:** 앞뒤 같은 위치, 회전한 벽, Scale `(5,0.1,5)`에서 원 반지름과 사각형 월드 크기가 유지된다. 원본 Cube 치수가 100cm일 때만 이 Scale을 500×500×10cm로 해석한다.

**설명 질문:** “월드 좌표를 그대로 2D로 버리면 회전한 벽에서 왜 틀릴까?”

**남길 자료:** 좌표 축·피격점·단면을 겹쳐 그린 영상과 왕복 변환 오차 테스트.

## M03. 남은 벽 영역을 계산하기

**배울 것:** 외곽선·구멍·분리 영역, winding, 집합 차집합, 수치 오차.

**직접 할 일**

- [ ] 남은 재료를 여러 영역으로 저장하고, 각 영역의 외곽선과 구멍 소유 관계를 표현한다.
- [ ] 엔진 또는 외부 폴리곤 연산 후보를 확인한다. 다중 구멍, 분리 영역, 접점, 런타임/Server 사용, 라이선스를 작은 입력으로 평가한다.
- [ ] 원 한 개를 빼고, 겹치는 원을 빼고, 테두리를 가로지르는 사각형을 뺀다. 각각 2D 선으로 먼저 그린다.
- [ ] 좌표 정밀도와 최소 간격 정책을 정한다. 작은 총알 구멍을 임의로 없애는 오차 보정은 피한다.
- [ ] `변화 없음`, `유효한 빈 영역`, `계산 실패`를 구분한다. 실패가 벽 전체 삭제로 해석되지 않게 한다.
- [ ] 후보 결과가 유효할 때만 현재 영역을 교체한다. 이 단계의 고립된 조각은 정상 결과로 보관한다.

**완료 조건:** 동일 단면 반복, 100회 겹침, 접점/미세 간격, 테두리, 두 영역 분리, 전체 제거가 예상 그림과 일치한다. 순수 절단에서 남은 면적은 늘어나지 않고, 동일 입력 재적용은 형상을 바꾸지 않는다.

**설명 질문:** “구멍 목록만 저장하면 벽 밖으로 열린 구멍이나 두 조각으로 나뉜 벽을 표현할 수 있을까?”

**남길 자료:** 입력·기대 윤곽·실제 윤곽 사례집과 기하 테스트. 라이브러리 선택 이유 및 사용 버전.

## M04. 2D 영역으로 두께 있는 메시 만들기

**배울 것:** 구멍 포함 삼각분할, 정점/인덱스, winding, 법선, UV, 경계 연결.

**직접 할 일**

- [ ] 사각형 한 장을 삼각형으로 만들고, 내부 구멍 하나와 여러 구멍으로 확장한다.
- [ ] 모든 남은 영역에 대해 앞뒤 면을 만든다. 구멍을 삼각형으로 덮지 않는다.
- [ ] 외곽과 구멍 윤곽을 각각 앞뒤로 연결해 옆면을 만든다. 외곽/내곽 방향을 구분한다.
- [ ] 앞뒤 면 UV를 초기 패널 좌표에서 계산한다. 절단 후 Bounds가 줄어도 텍스처가 움직이지 않게 한다.
- [ ] 표면과 절단면의 재질 슬롯·법선을 정한다. DynamicMesh에서 이전에 관찰한 라이팅 문제도 비교한다.
- [ ] 생성한 월드 정점을 프록시 로컬로 저장할 때 Transform을 두 번 적용하지 않는지 확인한다.

**완료 조건:** 앞·뒤·구멍 안쪽에서 올바르게 보이고, 의도치 않은 열린 에지나 뒤집힌 면이 없다. 삼각형 면적 합이 남은 2D 면적과 허용 오차 내에서 일치한다. 전체 제거는 빈 메시로 처리한다.

**설명 질문:** “구멍이 뚫렸는데 메시 자체는 닫힌 재료 경계를 갖는다는 게 무슨 뜻일까?”

**남길 자료:** 와이어프레임, 법선·UV 비교, 구멍 내부 카메라 영상. 삼각분할과 extrusion을 별도 시간으로 기록한다.

## M05. 기존 무기와 플러그인에 연결하기

**배울 것:** 재사용 API, 상태 적용 시점, UObject 수명, 렌더·충돌의 역할 차이.

**직접 할 일**

- [ ] 실험 계산을 BreachSystem의 평면 벽 경로로 연결한다. 현재 3D 경로는 비교용으로 보존하고 사용 경로를 명확히 한다.
- [ ] `BindCylinder`와 `BindBox`의 게임 측 사용 의도를 유지한다. 게임 클래스명을 플러그인이 참조하지 않도록 의존성을 확인한다.
- [ ] 피스톨과 최소 해머 입력을 같은 파괴 API에 연결한다. 전용 근접 전투 시스템 전체를 추가할 필요는 없다.
- [ ] 메시가 처음 바뀔 때와 반복 갱신될 때 프록시·충돌 소유권을 확인한다. 원본과 프록시가 동시에 충돌하지 않게 한다.
- [ ] 영역·메시·충돌의 적용 버전을 관리한다. 충돌 준비 전 후속 피격을 처리할지 대기시킬지 정하고 오래된 충돌로 연속 판정하지 않게 한다.
- [ ] 완전 파괴, 액터 제거, 맵 종료 시 렌더·충돌·델리게이트를 정리한다.

**완료 조건:** 작은 구멍으로 사격이 통과하고, 충분히 큰 구멍으로 캐릭터 캡슐이 통과한다. 남은 재료는 계속 맞는다. 생성 실패는 이전 상태를 유지하고, 두 번째 피격도 같은 파괴 경로에 도달한다.

**설명 질문:** “화면에는 구멍이 있는데 서버 Trace가 벽을 맞는다면 어떤 상태가 뒤처진 걸까?”

**남길 자료:** 총알/해머 데모, 플러그인 사용 예시, 호출 순서와 소유 관계 그림. 여기까지가 로컬 기본 관통 기능이다.

## M06. 고립된 가운데 조각 제거하기

**배울 것:** 연결된 영역, 지지 조건, 절단과 붕괴 규칙의 차이.

**직접 할 일**

- [ ] 원본 패널 바깥 경계를 지지 경계로 사용하는 단순 정책을 만든다. 이 규칙은 자체 설계임을 기록한다.
- [ ] 절단 결과의 각 연결 영역이 지지 경계와 이어져 있는지 판정한다. 점 하나 접촉을 지지로 인정할지도 허용 오차와 함께 정한다.
- [ ] 지지를 잃은 영역을 남은 재료에서 제거하고 메시·충돌을 재생성한다.
- [ ] 가장 큰 영역만 남기는 방식은 쓰지 않는다. 양쪽이 각각 지지되는 분리 벽은 모두 유지한다.
- [ ] 열린 고리와 아주 얇은 연결부는 아직 연결된 것으로 취급한다. 약한 연결부 파괴는 누적 규칙과 구분한다.

**완료 조건:** 고리를 닫는 마지막 절단에서 가운데가 사라지고, 열린 고리에서는 남는다. 지지된 두 영역은 모두 유지되며 사라진 조각의 충돌도 사라진다.

**설명 질문:** “Difference가 정상인데 가운데 조각이 남는 이유는 무엇일까?”

**남길 자료:** 열린 고리/닫힌 고리/양쪽 지지의 세 비교 영상. 파편이 떨어지는 연출은 별도 확장이다.

## M07. 가까운 곳을 여러 번 쏘면 크게 부서지게 만들기

**배울 것:** 공간적인 누적 상태, 임계값, 게임 규칙과 기하학의 분리.

**직접 할 일**

- [ ] 유효 피격 주변의 파괴 영향을 모을 간단한 공간 단위를 정한다. 고정 2D 셀부터 실험하되 셀 경계 양쪽 피격이 부자연스럽게 갈리는지 확인한다.
- [ ] 누적량, 영향 범위, 발동 기준, 추가 절단 패턴을 정의한다. HP Damage와 같은 수치를 쓰려면 변환 정책을 게임에서 명시한다.
- [ ] 기준을 넘으면 큰 단면을 추가로 빼고, M06의 지지 판정을 다시 수행한다.
- [ ] 큰 파괴 이후 관련 누적 상태를 정리해 같은 손상으로 무한 재발동하지 않게 한다.
- [ ] 형상이 바뀌지 않아도 실제 재료를 맞았다면 누적량이 변할 수 있음을 처리한다. 빈 구멍을 통과한 탄환은 해당 벽 피격으로 누적하지 않는다.
- [ ] 순서를 `유효 피격 → 직접 절단/누적 → 추가 절단 → 지지 판정 → 메시·충돌 적용`으로 확인한다.

**완료 조건:** 같은 발수라도 밀집 사격과 분산 사격의 결과가 다르고, 큰 절단 후 고립된 조각도 정리된다. 선택한 수치와 결과를 본인이 설명할 수 있다.

**설명 질문:** “이미 있던 구멍 근처의 벽을 맞았는데 도형이 안 바뀌었다면 피격 처리 전체를 종료해도 될까?”

**남길 자료:** 누적량 디버그 표시, 밀집/분산 영상, 파괴 규칙 표. 공개 자료의 확정 구현과 자체 규칙을 구분한다.

## M08. 서버가 사격과 파괴를 결정하게 만들기

**배울 것:** authority와 ownership의 차이, Server RPC, 서버 Trace, 직렬 처리 순서.

**직접 할 일**

- [ ] 클라이언트의 조준 입력과 서버의 실제 피격 판정을 분리한다. 현재 화면 중앙 Deproject를 서버에서 그대로 실행하지 않는다.
- [ ] 클라이언트가 소유한 Pawn/Controller 등 적절한 객체를 통해 요청한다. 소유하지 않은 벽에 Server RPC를 직접 보내는 구조를 피한다.
- [ ] 서버가 무기 소유, 발사 간격, 탄약, 사거리, 조준 입력의 허용 범위를 확인한다. 단면 크기·벽 파괴량은 서버의 무기 설정에서 가져온다.
- [ ] 서버 Trace 결과로 벽에 명령을 전달한다. 클라이언트가 보낸 HitResult나 큰 반지름을 그대로 권한 데이터로 쓰지 않는다.
- [ ] 피격 ID·벽 상태 버전으로 중복 적용을 막고, 같은 벽의 동시 요청을 서버가 정한 순서로 처리한다.
- [ ] 데디케이트 서버에도 최신 사격/이동 충돌을 유지한다. 화면용 재질·이펙트는 필요 없어도 판정용 형상은 필요하다.

**완료 조건:** 두 클라이언트가 같은 곳을 쏴도 서버에서 한 번씩 순서대로 적용되고, 클라이언트가 바꾼 반지름·연사 간격으로 권한 상태를 바꿀 수 없다. 서버 충돌 준비 전후 처리 정책이 연속 사격에서도 지켜진다.

**설명 질문:** “벽을 내가 보고 있다는 것과 그 벽의 RPC를 호출할 소유권이 있다는 것은 같은 뜻일까?”

**남길 자료:** 클라이언트 요청→서버 판정 흐름, 승인/거부 로그, 동일 벽 동시 사격 실험. RPC의 실행 위치는 소유권에 영향을 받는다. [Epic RPC 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-procedure-calls-in-unreal-engine)

## M09. 파괴 상태 복제와 중도 접속 복구

**배울 것:** 지속 상태와 일회성 이벤트, 버전, 스냅샷, relevancy, 초기화 순서.

**직접 할 일**

- [ ] 첫 버전은 서버의 확정된 2D 영역을 복제하고 클라이언트가 메시를 재생성하게 한다. 월드 Transform·초기 규격·단면 정책을 포함해 재구성에 필요한 정보를 정한다.
- [ ] 벽 식별, 라운드/초기화 세대, 상태 Revision을 구분한다. 복제된 영역으로 복원할 때 누적 파괴를 다시 실행하지 않는다.
- [ ] 최신 상태 하나만 받아도 복원이 되도록 만든다. 모든 중간 피격이 반드시 OnRep로 전달된다고 가정하지 않는다.
- [ ] Snapshot의 영역·구멍·버전이 모두 준비된 후 적용한다. 상태가 커지면 전송 크기를 측정하고, 분할 전송 시 같은 Revision의 완성본만 게시한다.
- [ ] 새 클라이언트의 초기 상태 수신과 맵/컴포넌트 준비 순서를 처리한다. 멀리 있다가 벽이 relevant해진 경우도 같은 복구 경로로 처리한다.
- [ ] 이전 Revision·중복 결과·라운드 종료 후 도착한 결과를 버린다. 클라이언트 재구성 실패 시 진단과 재동기화 경로를 둔다.
- [ ] 서버에만 필요한 누적 손상 값과 클라이언트에 필요한 표현 상태를 구분한다. 클라이언트에서 누적량을 보여주지 않는다면 모두 복제할 이유는 없다.

**완료 조건:** A가 벽을 50회 파괴한 후 B가 접속해 같은 윤곽과 충돌을 재현한다. B가 복원하는 동안 A가 더 쏴도 최종 Revision으로 수렴한다. 관련성 재진입, 재접속, 패킷 손실 후에도 상태가 복구된다.

**검증 방법:** 같은 Revision의 영역 면적·구멍/영역 수와 고정 Trace 지점의 통과/차단을 비교한다. 해시를 쓴다면 좌표 양자화·윤곽 정렬부터 정의하며 메시 정점 순서가 같다고 가정하지 않는다.

**설명 질문:** “Multicast로 총알 자국을 모두 보냈는데 나중에 들어온 플레이어의 벽은 왜 복원되지 않을까?”

**남길 자료:** 중도 접속/동시 파괴 영상, 상태 형식, Revision 로그, 동기화 검증표. 상태 복제는 [Epic 프로퍼티 복제 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/replicate-actor-properties-in-unreal-engine), 현재 연결에 대한 RPC 범위는 [Epic RPC 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-procedure-calls-in-unreal-engine)를 읽는다.

이벤트만 보내 같은 연산을 재연하는 방식은 이후 최적화 후보다. 같은 입력이라고 부동소수점·기하 라이브러리 결과가 모든 환경에서 같다고 가정하지 않는다. 채택한다면 입력 양자화·순서·알고리즘 버전과 스냅샷 복구가 추가 과제다.

## M10. GameFeature로 장착하고 수명 관리하기

**배울 것:** 플러그인 의존 방향, GameFeatureData/Action, 활성화와 등록, 월드·액터 수명.

**직접 할 일**

- [ ] `게임 → GameFeature → BreachSystem`의 역할을 정한다. BreachSystem은 총기·특정 맵·GameFeature를 역참조하지 않는다. 게임이 Core 공개 API를 쓰는 의존성과 Feature 전용 콘텐츠 의존성을 구분한다.
- [ ] GameFeature에 사용할 벽/무기 설정과 장착 동작을 묶는다. 단순히 폴더만 옮기지 말고 활성화가 기능 등록을 실제로 담당하게 한다.
- [ ] 기존 대상과 활성화 이후 생성된 대상에 모두 기능이 붙는지 확인한다. Add Components를 쓰면 대상 Actor의 receiver 등록/해제와 중복 장착 방지를 확인한다.
- [ ] 서버와 각 클라이언트에서 Feature를 로드·활성화한다. 서버의 활성화 호출이 자동으로 모든 클라이언트를 활성화한다고 가정하지 않는다.
- [ ] 기능 준비 상태와 벽 상태 복원을 완료한 클라이언트만 해당 플레이를 시작하도록 연결한다. 중도 접속도 준비→최신 상태 복원 순서로 진행한다.
- [ ] 라운드 종료 시 신규 요청을 막고 진행 중 작업을 마무리/무효화한 뒤, 주입 컴포넌트·델리게이트·프록시·등록 데이터를 정리한다.
- [ ] 다음 라운드 활성화에서 새 세대의 초기 벽 상태로 시작한다. 이전 콜백이나 네트워크 결과가 새 벽을 변경하지 못하게 한다.

**완료 조건:** 활성화·플레이·라운드 종료·비활성화·재활성화를 5회 반복해 중복 피격/충돌/등록이 없다. 기능이 비활성인 세션도 기본 게임이 시작된다. 서버·클라이언트·중도 접속이 같은 생명주기를 따른다.

**설명 질문:** “GameFeature를 껐을 때 그 기능이 등록한 델리게이트와 생성한 객체는 누가 정리할까?”

**남길 자료:** 의존성 그림, 활성화/정리 로그, 반복 영상. 기능 활성화와 코드 모듈의 물리적 언로드는 구분한다. [Epic GameFeature 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/game-features-and-modular-gameplay-in-unreal-engine)

## M11. 패키징과 재사용으로 통합 검증하기

**배울 것:** 런타임/에디터 의존성, cook 대상, 콘텐츠 참조, 재현 가능한 배포.

**직접 할 일**

- [ ] 완성한 Feature 콘텐츠·머티리얼·기하 의존성을 포함해 서버와 클라이언트를 build/cook/package한다. M01의 작은 맵 성공만으로 최종 패키징을 대신하지 않는다.
- [ ] 에디터를 닫고 패키징한 서버 1개, 클라이언트 2개를 실행한다. 중도 접속용 클라이언트 1개를 나중에 추가한다.
- [ ] 모든 핵심 파괴 규칙, 충돌, GameFeature 준비·정리, 늦은 접속을 실제 실행 파일에서 확인한다.
- [ ] 다른 최소 프로젝트에 Core 플러그인과 Feature를 옮긴다. 필요한 의존성·Actor 등록·설정만으로 벽 한 장과 피격 입력을 연결한다.
- [ ] 플러그인에 남아 있는 BreachTest 클래스/콘텐츠 경로 의존성을 제거한다. 샘플 콘텐츠와 재사용 필수 콘텐츠를 문서에서 구분한다.
- [ ] 에디터 전용 모듈이 Server 빌드에 필요하지 않게 의존성을 확인하고, 외부 라이브러리 라이선스를 함께 제공한다.

**완료 조건:** 다른 프로젝트에서 핵심 파괴가 실행되고, 원본 프로젝트의 최종 데디케이트 서버 데모가 에디터 없이 재현된다. 최종 데모에서 서버·클라이언트가 같은 패키지/규칙 버전을 사용한다.

**설명 질문:** “다른 프로젝트로 옮기기 위해 내 게임의 무기 클래스를 가져와야 한다면 어디가 잘못 결합된 걸까?”

**남길 자료:** 설치·실행 README, 최소 이식 프로젝트, 패키징 로그, 서버+클라이언트 재현 영상.

## M12. 성능과 포트폴리오 마무리

**배울 것:** 병목 측정, 평균과 긴 프레임의 차이, 대역폭, 재현성과 근거.

**직접 할 일**

- [ ] 장비·엔진 버전·빌드 구성·벽 크기·원 분할 수·동시 벽 수·발사 간격을 고정하고 기록한다.
- [ ] 누적 1/10/50/100회 피격에서 클리핑·삼각분할·메시 적용·충돌 준비 시간을 나눠 측정한다. 서버 게임 스레드와 클라이언트 프레임을 따로 본다.
- [ ] 중앙값/p95/최댓값, 실패 수, 정점/삼각형 수, 메모리, 전송량/초, 중도 접속 상태 크기·복원 시간을 기록한다.
- [ ] 기존 3D 경로와 새 경로의 단순 관통을 동일 조건으로 비교한다. 고립 제거·누적 파괴가 켜진 결과를 동일 형상 성능 비교라고 제시하지 않는다.
- [ ] 측정 후 서버 tick 예산·클라이언트 프레임 예산·허용 복원 시간·최대 상태 크기의 목표치를 정하고 검증한다. 임의의 개선율을 미리 적지 않는다.
- [ ] 가장 큰 병목 하나를 개선하고 전후를 비교한다. 전체 재삼각분할, 충돌 갱신, 전송 크기 중 실제로 큰 항목부터 한다.
- [ ] 작업을 비동기로 옮긴다면 UObject 접근 경계·Revision·취소·늦게 끝난 결과 폐기를 검증한다. 비동기를 필수 기능으로 늘리지 않는다.
- [ ] 최종 영상, 구조 그림, 실패→개선 기록, 성능표, 지원 범위/한계, 직접 구현한 부분/외부 기능 사용 부분을 정리한다.

**완료 조건:** 아래 최종 검증표에 증거가 있고, 수치가 어떤 조건에서 나온 것인지 다른 사람이 재현할 수 있다. 목표를 못 맞춘 항목은 남은 한계로 명시하며 성공으로 체크하지 않는다.

**설명 질문:** “총알 한 발은 빨라졌는데 100발 뒤 긴 프레임이 남는다면 최적화가 완료됐다고 할 수 있을까?”

**남길 자료:** 2~3분 데모, 1장 구조도, 측정 원본과 그래프, 핵심 의사결정 기록. 제목 예시: ‘GameFeature 기반 서버 권한형 실시간 벽 파괴 플러그인’.

## 5. 최종 검증표

목표 시나리오이지 이미 통과한 결과가 아니다. 완료할 때 빌드/커밋·실행 조건·증거 경로를 각 항목에 기록한다.

| 분야 | 필수 사례 | 완료 판정 |
| --- | --- | --- |
| 형상 | 최초·동일 위치·100회 겹침·접점·모서리·전체 제거 | 유효한 영역과 메시, 실패 시 이전 상태 보존 |
| 좌표 | 앞뒤·회전·비균일 Scale | 월드 단면 크기 유지 |
| 지지 | 열린 고리·닫힌 고리·양쪽 지지 | 규칙과 일치하는 제거, 충돌도 일치 |
| 누적 | 같은 발수 밀집/분산·빈 공간 사격 | 공간별 누적, 빈 공간 미집계 |
| 서버 판정 | 동시 피격·중복 요청·부당한 발사 입력 | 서버가 허용한 순서와 값만 적용 |
| 중도 접속 | 50회 파괴 후 접속·복원 중 추가 피격 | 최신 상태 수렴, 사격/이동 충돌 일치 |
| 통신 | 지연·손실·관련성 재진입·재접속 | 영구 불일치 없음, 복구 시간 기록 |
| Feature | 활성화/정리/재활성화 5회·늦은 접속 | 중복 등록·남은 충돌·이전 세대 적용 없음 |
| 수명 | 맵 종료·벽 제거·라운드 리셋 | 콜백/작업/프록시 정리 |
| 배포 | 실제 서버+클라이언트·다른 프로젝트 이식 | README로 재현 가능 |
| 비용 | 1/10/50/100회·여러 벽·서버/클라이언트 분리 계측 | 목표 대비 결과와 한계 기록 |

통신 테스트는 우선 지연·손실 없는 환경에서 통과시킨다. 다음은 예시 조건으로 RTT 약 100ms와 손실 1%, RTT 약 200ms와 손실 5%를 추가한다. 도구 설정값이 단방향 지연인지 확인하고 실제 관측 RTT·손실을 기록한다. 이 수치는 제품 보장 사양이 아니라 검증을 시작할 실험 조건이다.

## 6. 이번에 바로 시작할 작은 작업

1. 기존 피스톨 한 발이 프록시 메시 변경까지 가는 호출 흐름을 직접 그린다.
2. 각 화살표 옆에 입력 데이터와 상태 소유자를 적는다.
3. 같은 위치 3회/겹치는 위치 3회/테두리 1회 입력을 고정해 현재 결과를 기록한다.
4. Server Target과 BuildProject.bat의 Editor 전용 부분을 읽고, 서버 실행을 위해 바꿀 목록을 본인이 적는다.
5. 그 목록을 구현·검증한 다음 M02의 좌표 디버그 실험으로 간다.

처음부터 삼각분할·복제·GameFeature를 동시에 구현하지 않는다. 위 작은 작업 하나를 끝낸 뒤 다음 작업으로 간다.
